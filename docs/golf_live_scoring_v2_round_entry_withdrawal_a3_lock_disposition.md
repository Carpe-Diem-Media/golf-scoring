# GLS-42A A3 lock disposition for RoundEntry withdrawal

- **Status:** PROPOSED, NOT ADOPTED
- **Task:** GLS-42A-A3-L0 (amendments GLS-42A-A3-L1 and GLS-42A-A3-L1b)
- **Reviewed baseline:** `main` at `51f02b35f0aad9e728dbaad6b8bbf88597d9b608`
- **Scope:** Lock order and caller compatibility for a future in-round withdrawal acceptance coordinator. No production code, migration, acceptance action, status mutation, or GLS-30 change is authorized by this proposal.

## Disposition

The existing top-level submission and role-handover paths share the Round row as their first gameplay lock. That row can serialize withdrawal with those paths. A `RoundEntry` row lock after the existing Round, PlayingGroup, and GroupRoleAssignment locks would not require a new GLS-30 class for the inspected top-level paths.

This is not enough to adopt the candidate. Four decisions remain for owner approval:

1. **Transaction boundary:** public commands that can lock Round, PlayingGroup, active role assignments, affected Side/SideResult rows, or RoundEntry must reject arbitrary outer transactions before their first lock. The Ash registration actions need a pre-transaction check; their current `before_action` guard runs too late to establish this boundary. Lower-level lock helpers and private writes may compose only inside a coordinator that owns the transaction and acquires the approved lock prefix first.
2. **Side recalculation:** derive each Side contribution from accepted HoleResults at the authoritative rotated route index and the immutable A2 ruling's `effective_play_index`. Preserve results before that boundary; do not erase history by filtering on the RoundEntry's current `withdrawn` status. Do not persist duplicate score totals. When a withdrawal creates a verification or eligibility blocker, use the guarded `provisional → review_required` transition. Lock affected CompetitionSide and CompetitionSideResult rows in existing GLS-30 order before RoundEntry.
3. **Physical pre-play evidence:** a prior receipt and a next-unsubmitted route position do not prove that physical play on that next hole has not begun. Require an explicit, contemporaneous attestation by the accepting Event Admin or Competition Manager that the exact effective hole is unstarted, and record its scoped provenance in the acceptance audit. The A2 boolean alone is not proof.
4. **Roles and continuation:** accept withdrawal as a participation fact even if competitive scoring must pause. Make any role assignment held by that entry `revoked` permanently; ordinary handover cannot restore a revoked assignment. Propose a separate authorized vacancy-fill operation that creates a new active assignment at the next role revision, validates independent verification, and audits its link to the withdrawal. If verification is unavailable, use an evidence-guarded `playing → attention_required` transition and block scoring. Clear attention only after an authorized recovery confirms valid scorer/verifier coverage and no unresolved attention blocker. Preserve Side membership and do not waive independent verification.

The recommendations are detailed in the owner-decision amendment below and remain **PROPOSED, NOT ADOPTED**. Keep GLS-30 and frozen authority unchanged. The source characterization tests do not prove a withdrawal coordinator that does not exist.

## Proposed lock order, subject to owner approval

For a supported top-level staff acceptance, the candidate sequence is:

1. Begin a standalone `Repo.transaction/1`. Reject an already-open application transaction before acquiring any row lock.
2. Call `EventAuthorityLock.lock_scope!/2` for the Event and accepting staff member. Revalidate the active Event Admin or Competition Manager assignment while these locks remain held.
3. Call `LockProtocol.acquire!/1` for the target Round and PlayingGroup. It locks Round before PlayingGroup.
4. Read active GroupRoleAssignment IDs for that group and lock them through `LockProtocol.acquire!/1`. The protocol sorts IDs before `FOR UPDATE`.
5. Read the RoundEntry's affected CompetitionSide IDs while the Round lock excludes membership changes. Lock those CompetitionSide and corresponding CompetitionSideResult rows through `LockProtocol.acquire!/1`, in the existing GLS-30 class and UUID order.
6. Lock the target RoundEntry with a scoped `SELECT ... FOR UPDATE`. Revalidate its Event, Round, PlayingGroup, registration state, and `participation_status` from the locked row.
7. Read the route and accepted submission checkpoint, validate the server checkpoint and positive physical pre-play attestation, then write accepted A2 evidence, the `active` to `withdrawn` status change, any withdrawal-caused role termination and readiness blockers, and the required audit in the same transaction.
8. Commit. Publish any client notification only after commit.

`RoundEntry` is not a GLS-30 relation class. This proposal treats its explicit row lock as a scoped extension after the existing GLS-30 classes. It does not add a `:round_entry` key to `LockProtocol`, and it does not authorize acquiring any later GLS-30 class after that entry lock. The proposed withdrawal-caused readiness write is protected by locking CompetitionSide and CompetitionSideResult before RoundEntry. A3 must fail closed when the standalone transaction requirement is not met.

### Explicit and implicit database locks

`LockProtocol.acquire!/1` uses one-row-at-a-time `SELECT ... FOR UPDATE` and canonical UUID ordering for `R`, `G`, and `A`. The direct entry locks in the services above use `SELECT ... FOR UPDATE`; `SubmitGroupHole` locks all required entries in `ORDER BY id` order. Ash updates later update rows already locked by the same transaction. Inserts into A2 and audit tables also cause PostgreSQL foreign-key checks to take key-share locks on referenced rows. The candidate must hold the mutable parent rows through the same transaction and must not acquire a new earlier lock after the Entry lock.

## Withdrawal lifecycle and role guard

The proposed acceptance transition is `active` to `withdrawn` only.

- Accept only through an active Event Admin or Competition Manager assignment for the same Event. A player or scorer may request withdrawal, but the acceptance actor must satisfy the adopted A1 authority rule.
- Require an explicit reason and audit it. A2 does not store a reason field, so A3 must preserve it in the accepted audit record required by the frozen specification.
- Reject `not_started`, `completed`, `withdrawn`, and `disqualified` for ordinary in-round withdrawal. `not_started` uses the existing `withdraw_before_start` registration action and does not create an in-round participation ruling.
- Lock and re-read all active assignments for the group. If the target holds an active scorer or verifier assignment, mark that assignment `revoked` in the acceptance transaction and audit its ID, role, prior holder, and withdrawal ruling. `revoked` is terminal for that row; do not change it back to `active` or create a successor during withdrawal.
- Check that remaining active scorer and designated-verifier assignments provide the independent verification required by frozen §46. If they do not, accept the withdrawal fact, leave the old assignment revoked, set the PlayingGroup to `attention_required`, and set an affected `provisional` SideResult to `review_required` with coordinator evidence. Block competitive scoring until a separately authorized vacancy recovery restores valid role coverage and clears the A3-owned attention blocker. Do not waive independence. If independent verification remains valid, leave the group playing.
- A withdrawal must not clear or replace an attention state that predates this acceptance. If the group is already `attention_required`, record the withdrawal and preserve that state; recovery requires evidence for every outstanding attention cause. If provenance is absent or ambiguous, keep the group blocked.
- Insert the accepted A2 evidence, update the target `RoundEntry.participation_status`, end any target-held active role, apply required group/SideResult blocker states, and write the audit in one local transaction. Any failure rolls back all effects. Do not edit existing HoleResults, change CompetitionSideMembership, or call `MysteryRevealCoordinator` as part of this acceptance.
- After commit, notify clients if needed. A failed or rolled-back acceptance must emit no PubSub event.

The frozen spec's §§61.8 and 62.4 require recalculating dependent Side results (`docs/golf_live_scoring_v2_spec_v1.0.md:8256-8263,8616-8623`). The proposed per-hole A2 effective-boundary applicability, SideResult source-state/guard matrix, and post-commit notification contract are defined in owner-decision section 2 below. `CompetitionSideResult` persists lifecycle/readiness state and pre-play exclusion evidence but no score totals (`lib/golf_scoring/competition/competition_side_result.ex:172-215`). Do not persist duplicate score totals or filter all prior HoleResults by current participation status.

## Checkpoint and ambiguity rules

The submission code already defines the authoritative route calculation (`lib/golf_scoring/scoring/services/submit_group_hole.ex:1002-1039,1070-1103`). It reads the 18 `RoundHole` rows by `play_order`, rotates that route at `PlayingGroup.starting_round_hole_id`, and selects the hole at the locked `scoring_revision`. A3 can reuse those persisted facts only after it holds `R` and `G` and re-reads them.

For an in-play withdrawal with accepted scoring, let `n` be the locked group `scoring_revision`:

- Require `1 <= n < 18`, an assigned start hole in the valid 18-hole route, and a target Entry whose locked participation state is `active`.
- Require exactly one accepted `HoleSubmission` for the latest accepted group revision, with `expected_group_score_revision = n - 1` and `round_hole_id` equal to the rotated route element at `n - 1`.
- Set `checkpoint_play_index = n - 1` and the effective next unsubmitted hole to the rotated route element at index `n`. Set `effective_play_index = n`.
- The route, group start, current revision, and prior accepted receipt establish the server checkpoint only. They do not establish physical play has not begun on the next hole. The current `PlayingGroup.state` is group-level, and `scoring_revision` advances only on accepted submissions; neither records a physical start for each hole.
- Proposed attestation contract: before the database transaction, the accepting active Event Admin or Competition Manager must personally make a direct visual check of the group at the starting area of the exact effective hole and confirm that no group member has begun play there. The staff member submits `observed_at` and the attestation in the same acceptance request; the server records `attested_at` on receipt and requires `observed_at` to be no later than `attested_at` and, under the proposed freshness rule, no more than 60 seconds earlier. The 60-second limit is a proposal for owner approval, not an established safety guarantee. The attestation documents the authorized staff member's observation; software cannot independently prove the physical play state. The transaction then derives the authoritative checkpoint and accepts only if the attested Round, PlayingGroup, effective hole ID, and play index match it. The immutable acceptance audit records the actor and verified role, `observed_at`, `attested_at`, observation method and location, Round and PlayingGroup, target RoundEntry, checkpoint submission/hole/index, current revision, effective hole/index, withdrawal reason, and the affirmative assertion. The A2 row's `authorized_by_staff_user_id`, `authorized_by_role`, `accepted_at`, and `preplay_boundary_confirmed` carry authority, time, and the required true flag; its boolean alone cannot supply the observation basis (`lib/golf_scoring/competition/round_entry_participation_ruling.ex:112-149`).
- Reject when the staff member cannot personally make that check, the attestation is absent or unclear, `observed_at` exceeds the proposed 60-second freshness limit or is later than server-recorded `attested_at`, or its scope differs from the locked checkpoint. Second-hand reports, route inference, and assumptions are insufficient. Rejection leaves applicability unknown and writes no evidence or status.
- Existing precedent requires an explicit `confirm_hole_unplayed?` input and records it in the acceptance audit context for pre-play Side exclusion (`lib/golf_scoring/competition/services/exclude_competition_side_before_hole.ex:47-50,96-103,513-529`). A3 must bind that affirmative assertion to the server-derived withdrawal checkpoint and include the richer provenance above; do not infer it from route data.
- Reject missing, duplicate, stale, or route-mismatched checkpoint rows; a missing start hole; a route other than the expected 18 holes; a completed group; or a client-supplied checkpoint that differs from the locked facts. Rejection writes nothing.

A zero-submission group is distinct from an active participant withdrawing after accepted scoring. The current scoring lifecycle can mark an Entry `active` only after a valid accepted HoleResult exists in the same SubmitGroupHole transaction. The A2 evidence shape also requires non-null checkpoint submission and checkpoint hole references. Therefore, if `n = 0`, an ordinary active-entry withdrawal is invalid. Reject an inconsistent `active` Entry with no accepted submission; use the existing pre-start registration withdrawal for a `not_started` Entry. Do not fabricate a checkpoint submission or effective-play evidence.

## Required A3 integration tests

After this disposition and its open authority questions are approved, use independent PostgreSQL sessions, transaction barriers, and bounded lock/test timeouts. Exercise the actual acceptance coordinator and assert final database state, not only return values.

If a readiness write occurs, assert CompetitionSide and CompetitionSideResult locks precede `RoundEntry` in GLS-30 order.

## Owner-decision amendment: four proposed contracts

This section resolves the analysis questions with concrete recommendations for owner approval. It does not adopt them. The file status remains **PROPOSED, NOT ADOPTED**, and A3 implementation remains out of scope.

### 1. Transaction ownership

**Source evidence.** `SubmitGroupHole` rejects an existing transaction in its standalone wrapper (`lib/golf_scoring/scoring/services/submit_group_hole.ex:280-282`), and `VerifyHoleResult` checks before `Repo.transaction/1` (`lib/golf_scoring/scoring/services/verify_hole_result.ex:27-40`). `HandoverGroupRole`, `AssignGroupRole`, `RevokeGroupRole`, and `ReplaceRoundEntry` start transactions without that precheck (`lib/golf_scoring/competition/services/handover_group_role.ex:21-49`; `lib/golf_scoring/competition/services/assign_group_role.ex:17-42`; `lib/golf_scoring/competition/services/revoke_group_role.ex:17-43`; `lib/golf_scoring/competition/services/replace_round_entry.ex:18-47`). The pre-open guards execute after Event authority and Round locks, so they cannot prevent a lock cycle caused by a caller that already holds a later row. The Ash registration actions declare `transaction? true` and their resource change adds `before_action` (`lib/golf_scoring/competition/round_entry.ex:66-92`; `lib/golf_scoring/competition/round_entry_lifecycle_guard.ex:15-43`).

**Proposed contract.** Public commands listed in the transaction-boundary table are standalone-only. They return `:transaction_already_open` before acquiring any lock. For the Ash actions, use a `before_transaction` hook or an outer public wrapper. Keep internal state writes composable only within their owning transaction coordinator after it has acquired the approved lock prefix. No arbitrary caller-owned transaction is supported. The located production callers invoke these services directly from LiveView or plain `Competition` wrappers; no production caller change is identified.

**Acceptance tests.** For each guarded service and Ash registration action, call it from an outer transaction that already holds a row later in the order and assert the command rejects before waiting on Event authority or Round. Add a top-level call for each current production caller and preserve its existing result. Run submission-vs-withdrawal and handover-vs-withdrawal barriers in both lock-winner orders; assert final rows, audit, revisions, and notifications.

### 2. Side recalculation and persisted readiness

**Source evidence.** Frozen §§61.8 and 62.4 require dependent Side recalculation (`docs/golf_live_scoring_v2_spec_v1.0.md:8256-8263,8616-8623`). `CompetitionSideResult` persists readiness state and exclusion provenance but no score totals (`lib/golf_scoring/competition/competition_side_result.ex:172-215`). The Four-Ball and solo contribution calculators are pure (`lib/golf_scoring/scoring/calculators/four_ball_best.ex:1-20`; `lib/golf_scoring/scoring/calculators/solo_normalization.ex:1-35`). Frozen §62.6 uses `review_required` for verification or eligibility blockers (`docs/golf_live_scoring_v2_spec_v1.0.md:8640-8649`). The current lifecycle guard rejects generic `mark_review_required` without verified coordinator evidence (`lib/golf_scoring/competition/competition_side_result_lifecycle_guard.ex:11,30-36,166-174`).

**Proposed applicability contract.** For each accepted HoleResult belonging to the withdrawn RoundEntry, resolve its `play_index` through the authoritative rotated `RoundHole` route and compare it with that entry's single immutable A2 `round_withdrawal` ruling. Keep an otherwise valid historical result applicable when `play_index < ruling.effective_play_index`; treat the participant's contribution as not applicable from `effective_play_index` onward. Do not filter all of the participant's historical results because the current RoundEntry status is `withdrawn`, and do not rewrite or delete HoleResults. Use the ruling's `effective_round_hole_id` and `effective_play_index` together; reject or leave projection applicability unresolved if the ruling is absent, inconsistent, or ambiguous. The effective index is per-hole, not a whole-round status switch.

**Proposed SideResult source-state/guard matrix.** A3 locks each affected Side and SideResult before the RoundEntry row. Its conditional readiness write requires coordinator evidence bound to the accepted ruling, affected Side, locked source state, exact blocker, and post-revocation role/eligibility snapshot.

| Locked source state | A3 outcome | Guard and evidence |
|---|---|---|
| `provisional` | Keep `provisional` when no readiness blocker exists; transition to `review_required` only when the withdrawal creates a concrete eligibility or independent-verification blocker. | Verified withdrawal-coordinator evidence must identify the blocker and ruling. A withdrawal alone is not a blocker. |
| `review_required` | Preserve `review_required`; do not downgrade it or replace existing review evidence. | The withdrawal ruling and audit are recorded separately. No SideResult state write is needed. |
| `ready_to_finalize` | Reject and roll back A3 acceptance; do not silently invalidate or overwrite readiness. | The current lifecycle contract supplies no A3-authorized `ready_to_finalize → review_required` transition. An owner-approved transition is required before accepting from this source state. |
| `finalized` or `excluded` | Reject and roll back A3 acceptance; preserve the terminal state and all exclusion/finalization evidence. | A3 does not reopen a finalized result or reverse an exclusion. The frozen §62.6 exception paths remain separate. |

The precise blocker is a failed frozen eligibility rule or a post-withdrawal role map that cannot independently verify required HoleResults. Do not mark a SideResult `review_required` merely because a RoundEntry is withdrawn. The current retirement review guard accepts `provisional → review_required` and leaves an already `review_required` result unchanged when evidence is valid; generic review writes still require a verified coordinator (`lib/golf_scoring/competition/competition_side_result_lifecycle_guard.ex:59-78,166-174`). This proposal adds only an A3-specific evidence-guarded `provisional → review_required` write. It does not add a SideResult state, change terminal states, or create a score-total record. Prior withdrawal contributions remain derived from per-hole A2 boundaries while readiness is under review. Lock affected CompetitionSides and CompetitionSideResults in UUID order after GroupRoleAssignment and before RoundEntry; acquire no GLS-30 class afterward.

Publish a round-scoped withdrawal/readiness notification only after commit so readers reload derived contributions and state. The existing score workflow uses `round:<id>` PubSub (`lib/golf_scoring/scoring/services/submit_group_hole.ex:293-314,841-846`); no withdrawal event or Side-projection subscriber was found. A3 must define and test the event payload without adding infrastructure. No failed or rolled-back transaction may publish.

**Acceptance tests.** Assert contributions before the A2 effective index remain applicable after withdrawal and later indexes do not contribute; assert current withdrawn status alone never erases historical results. Exercise every SideResult source state in the matrix, including rollback for `ready_to_finalize`, `finalized`, and `excluded`, and preservation of existing `review_required`. Verify no score-total row is written. Race the A3 readiness write with existing score-query/correction workflows and preserve GLS-30 order. Preserve Side membership and Mystery obligations.

### 3. Positive physical pre-play evidence

**Source evidence.** A2 stores the accepting staff user/role, `accepted_at`, checkpoint references, indexes, and `preplay_boundary_confirmed` (`lib/golf_scoring/competition/round_entry_participation_ruling.ex:112-149,165-188`). The database constraint requires the boolean to be true; it cannot establish what happened on the course (`lib/golf_scoring/competition/round_entry_participation_ruling.ex:95-99`). Existing pre-play exclusion requires an affirmative command value and copies it into audit context (`lib/golf_scoring/competition/services/exclude_competition_side_before_hole.ex:47-50,96-103,513-529`). Neither the route revision nor the accepted submission records whether players physically began the next hole.

**Proposed contract.** Before the database transaction, the accepting active Event Admin or Competition Manager personally makes a direct visual check of the group at the starting area of the exact effective hole and confirms no group member has begun play there. The staff member submits `observed_at` and the attestation in the same acceptance request. The server records `attested_at` on receipt and requires `observed_at` to be no later than `attested_at` and, under the proposed freshness rule, no more than 60 seconds earlier. The 60-second limit is a proposal for owner approval, not an established safety guarantee. This keeps the database transaction short while recording a contemporaneous staff assertion. The attestation documents what the authorized staff member says they observed; it is not independent proof of the physical play state. Under lock, A3 derives the authoritative checkpoint and rejects unless its Round, PlayingGroup, effective hole ID, and play index match the attestation. The immutable acceptance audit records the verified staff actor and role, `observed_at`, `attested_at`, direct-visual method and observation location, target scope, checkpoint and effective-hole facts, withdrawal reason, and affirmative assertion. Set A2's boolean only after validating this evidence. Reject absent, false, unclear, older-than-proposed-60-second, future, second-hand, inferred, or mismatched evidence. Software tests can validate the attestation's scope and persistence, not independently prove the physical observation.

**Acceptance tests.** Accept only an explicit positive, direct-visual attestation for the exact locked group and next hole. Reject missing/false attestation, missing method/location, an observation older than the proposed 60-second freshness limit, second-hand evidence, stale or client-selected checkpoint data, a route mismatch, or a hole the staff member cannot affirm is unstarted. On every rejection, assert no ruling, status, assignment, group state, SideResult state, audit, or PubSub mutation. On acceptance, assert all provenance is queryable from the immutable audit and A2 ruling.

### 4. Withdrawal, role authority, and continuation

**Source evidence.** Frozen §46 prohibits self-verification and defines the Primary Scorer/Designated Verifier coverage rules (`docs/golf_live_scoring_v2_spec_v1.0.md:6373-6382`); A1 D5 permits continuation only when the Side remains eligible and independent verification is available (`docs/golf_live_scoring_v2_round_entry_withdrawal_a1_adoption.md:9-14`). `GroupRoleAssignment` has `active`, `handed_over`, and `revoked` states; the internal revoke action accepts only an active row, and there is no action that restores a revoked row (`lib/golf_scoring/competition/group_role_assignment.ex:30-35,86-104`). `HandoverGroupRole.run/6` requires an active assignment for the requested role and returns `:no_active_assignment` when it is absent (`lib/golf_scoring/competition/services/handover_group_role.ex:32-43,156-160`). Its successor version is based on that active row (`lib/golf_scoring/competition/services/handover_group_role.ex:209-225`). Pre-open `AssignGroupRole` is limited to `draft` and `ready`, so it cannot fill an in-play vacancy (`lib/golf_scoring/competition/services/assign_group_role.ex:12-13,25-27`). Frozen §62.5 defines `attention_required`, and `SubmitGroupHole` rejects submissions in that state (`docs/golf_live_scoring_v2_spec_v1.0.md:8616-8623`; `lib/golf_scoring/scoring/services/submit_group_hole.ex:1054-1066`). The current PlayingGroup guard rejects both attention transitions until verified evidence is implemented (`lib/golf_scoring/competition/playing_group_lifecycle_guard.ex:48-57,78-82`).

**Proposed assignment lifecycle.** `active → revoked` is terminal for the old assignment. Withdrawal revokes and audits any target-held active role in the same transaction; it never creates a successor. Ordinary `HandoverGroupRole` cannot repair the resulting vacancy: it requires an active current assignment and will fail with `:no_active_assignment` after revocation. Do not describe a revoked assignment as handed over or reactivate it.

**Proposed vacancy-fill operation.** Add a distinct authorized in-play operation, provisionally named `FillGroupRoleVacancy`, for an authorized Event Admin, Competition Manager, or Scoring Support actor under the same Event, matching the existing in-play handover authority set (`lib/golf_scoring/competition/services/handover_group_role.ex:13`). It requires a `scoring_open` Round, the target group locked, the requested role to have no active holder, and the replacement to be an eligible active member of that group who holds no other active role. It creates a separate `active` assignment row at `max(assignment_version for that group and role) + 1` (or version 1 if no prior row exists), using the existing assignment identity and version constraints. It never updates the revoked row. The audit binds the vacancy, replacement, new role revision, actor, and accepted withdrawal ruling that caused the vacancy. The action uses the ordinary Round/PlayingGroup/GroupRoleAssignment prefix and locks the replacement Entry afterward; it is a standalone public command, not a nested transaction. It must not call `HandoverGroupRole` when there is no active assignment.

**Proposed PlayingGroup transition and recovery.** The withdrawal coordinator may change `playing → attention_required` only when its locked post-revocation role map fails frozen §46 independent-verification coverage. Record the withdrawal ruling ID, exact blocker, revoked assignment IDs/revisions, affected active entries, and actor in immutable audit evidence. A withdrawal that leaves verification intact does not flag attention. A withdrawal received while the group is already `attention_required` preserves that state and does not claim ownership of an earlier blocker. The current lifecycle guard must accept these transitions only with evidence from the owning coordinator; direct lifecycle writes remain rejected.

While `attention_required`, submission remains blocked. The authorized vacancy-fill operation creates a new role revision and may transition `attention_required → playing` in the same transaction only if the active role map then covers every required independent verifier under §46, the new assignment belongs to an eligible non-withdrawn participant, the role revision is current, the A3 withdrawal blocker is resolved, and no other attention cause remains. If the added assignment does not restore valid coverage, keep it active but leave the group `attention_required`; a later authorized fill may complete recovery. The transition uses the same authorized actor set and an evidence-bound lifecycle guard, not an unverified direct call to `clear_group_attention`. Its audit references the withdrawal ruling, original revoked assignments, replacement assignment IDs/revisions, evidence of independent-verification mapping, and actor. If any evidence or blocker is missing or ambiguous, retain `attention_required`; never clear it optimistically. SideResults remain `review_required` until normal readiness evaluation proves all readiness guards. Neither recovery transition changes Side membership, accepted HoleResults, or Mystery obligations.

Emit round-scoped `playing_group_attention_required`, `group_role_vacancy_filled`, and `playing_group_attention_cleared` notifications only after the owning transaction commits. The existing round topic is `round:<id>` (`lib/golf_scoring/scoring/services/score_query_notifier.ex:10-23`); A3 must define and assert payload scope and ensure rolled-back writes publish nothing.

**Acceptance tests.** Withdraw a scorer and verifier separately; assert the old assignment becomes revoked and its historical state never changes again. Assert ordinary handover returns `:no_active_assignment` and cannot restore it. Verify the authorized vacancy-fill action creates a distinct active assignment at the next role revision and rejects unauthorized actors, withdrawn/ineligible replacements, duplicate holders, and replacements holding another role. Race two fills and a fill against submission; assert Round serialization and one valid assignment result. When withdrawal leaves valid coverage, assert the group stays playing. When it removes independent verification, assert withdrawal commits, the group becomes attention-required, the SideResult follows the matrix, and new submission is rejected. Verify recovery clears attention only after current independent-verification evidence passes; otherwise it remains blocked. Assert preexisting attention is not cleared and ambiguous blocker provenance prevents recovery. Check notifications occur only after commit. Inject failures at role revocation, vacancy creation, attention update, SideResult update, evidence insert, RoundEntry update, and audit write; assert the owning transaction rolls back atomically.

## Performance and scope

Keep acceptance inside one short local PostgreSQL transaction. Use existing EventAuthorityLock and GLS-30 row locks, indexed scope lookups, and no HTTP or PubSub while locks are held. The current schema provides a Round/PlayingGroup index for RoundEntry, a RoundEntry participation index, a group index for role assignments, a unique `(round_id, play_order)` route index, and scoped HoleSubmission indexes. A group has at most four entries and a route has 18 holes, so the latest-receipt lookup is bounded to one group's submissions. `HoleSubmission` has no index on `expected_group_score_revision`; do not assume an index on that field.

The Round row serializes all groups in the same Round, as it already does for current writers. This proposal makes no throughput or 100,000-user readiness claim. It adds no Redis lock, polling, process registry, or new infrastructure.
